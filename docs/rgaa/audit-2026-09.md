## 1. Résultat

**Taux de conformité mesuré (méthode RGAA) : 72,6 %** — 53 critères conformes,
20 non conformes, 33 non applicables sur l’échantillon. Taux moyen par page :
88,5 %.

Méthode de calcul (celle du RGAA) : un critère est **conforme** s’il est
conforme ou non applicable sur chaque page de l’échantillon et conforme sur au
moins une ; **non conforme** s’il est non conforme sur au moins une page ;
**non applicable** s’il l’est partout. Taux = C / (C + NC). Le taux moyen est la
moyenne des taux calculés page par page.

**Après les correctifs de ce chantier : 100 % projeté** (73 C, 0 NC, 33 NA ;
taux moyen 100 %). Ce chiffre n’est **pas une mesure** : le serveur disponible
pendant l’audit sert le build d’avant les correctifs, et un nouveau build n’y
était pas permis. Ce qui le fonde :

- chaque correctif est écrit dans le code, relu, et couvert par un test
  unitaire quand il est vérifiable sans navigateur (`tests/unit/a11y-rgaa.test.tsx`,
  `convex/search.test.ts`, `convex/tribune.test.ts`) ;
- les trois specs E2E nouvelles (`tests/e2e/a11y-clavier.spec.ts`,
  `a11y-annonces.spec.ts`, `a11y-affichage.spec.ts`), jouées contre le build
  d’avant, **échouent exactement sur les non-conformités corrigées** (et
  passent partout ailleurs — détail au § 7). Elles doivent passer toutes après
  fusion et nouveau build : c’est le contre-audit automatisé.

La déclaration d’accessibilité (`/accessibilite`) affiche donc le taux
**mesuré** (72,6 %, « partiellement conforme ») et annonce le contre-audit ;
elle sera mise à jour avec le taux re-mesuré.

## 3. Méthode, outils, environnement

| Contexte de mesure | Ce qui est mesuré |
|---|---|
| fr · desktop · clair | axe-core (WCAG 2.0/2.1/2.2 A et AA + bonnes pratiques), relevé DOM (titres, repères, images, SVG, liens, champs, tableaux, cadres, médias, régions live, `lang`, `dir`), arbre d’accessibilité (`ariaSnapshot`), **séquence de tabulation complète** avec comparaison du style focalisé et du style au repos |
| ar · desktop · clair | idem |
| fr · desktop · sombre | axe-core (dont contraste) |
| fr · mobile · clair ; ar · mobile · sombre | axe-core, débordement horizontal |
| fr et ar · 320 × 640 | reflow (10.11) : `scrollWidth − clientWidth`, éléments qui sortent de la fenêtre, conteneurs défilants |
| fr · 640 × 400 @2x | zoom de page 200 % |
| fr · 1 280 px · texte ×2 | zoom du texte seul 200 % (tailles calculées doublées, comme le zoom texte de Firefox) ; textes rognés |
| fr (1 280 px) et ar (390 px) · espacement | 10.12 : interligne 1,5, lettres 0,12 em, mots 0,16 em, paragraphes 2 em |
| fr · mouvement normal / réduit | animations actives après 6 s (`document.getAnimations()`), rotation du globe (deux images du canevas à 2 s d’écart) |
| 915 × 412 et 1 280 × 256 | orientation paysage (13.9), hauteur 256 px (10.11) |

Outils : Playwright 1.61 et Chromium 141 (sans interface), axe-core 4.12.1,
html-validate 11 (DOM généré des 38 pages, préréglage `standard`), relevés et
parcours clavier écrits pour l’audit — les mêmes instruments sont désormais dans
`tests/e2e/_a11y.ts` (`parcourirAuClavier`, `lireIndicateurDeFocus`,
`debordementHorizontal`, `zoomerLeTexte`, `espacerLeTexte`, `textesRognes`).

Inspections dynamiques supplémentaires : palette de recherche ouverte (axe sur
le dialogue, séquence de tabulation, Échap), sélecteur de langue, menu mobile,
dialogue de confirmation du back-office, envoi des formulaires (erreurs puis
succès), focus après envoi (`document.activeElement`).

## 4. Limites — ce qui n’a PAS été vérifié

- **Aucun lecteur d’écran** (NVDA, JAWS, VoiceOver, TalkBack) n’est disponible
  dans cet environnement. À la place, on a vérifié ce que le lecteur d’écran
  **lit** : l’arbre d’accessibilité du navigateur (noms, rôles, états,
  propriétés — `ariaSnapshot`, `toHaveAccessibleDescription`), la présence et
  le contenu des régions live (`role="status"`, `role="alert"`), la gestion du
  focus. La **restitution vocale** elle-même — ce qui est réellement prononcé,
  dans quel ordre, avec quelle voix pour l’arabe et les changements de langue —
  reste à dérouler par une personne selon
  [`protocole-lecteurs-ecran.md`](./protocole-lecteurs-ecran.md). Les
  critères 7.1, 7.5, 8.7 et 8.10 en dépendent en partie.
- **Un seul moteur** : Chromium. Ni Firefox ni Safari (l’environnement de test
  RGAA en demande plusieurs) ; le zoom texte est émulé.
- Le **validateur W3C** n’était pas joignable (réseau) : 8.2 repose sur
  html-validate.
- Les contenus viennent de la base de développement (données de démonstration
  et billets laissés par les tests E2E dans la Tribune). Les contenus éditoriaux
  réels (actualités Sanity, PDF des membres, replays) ne sont pas dans
  l’échantillon — voir § 6.
